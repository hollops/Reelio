StreamMini API alignment

Before either of us builds further, we need one API contract that matches the PRD. I compared the endpoints in the Viora API reference against the StreamMini PRD the frontend is being built from. Below: what I'd like to adopt from your list, what's missing for PRD requirements, and a merged contract for us to agree on.

Capstone team · September 2026 · Draft v0.1

In short

  • Your list adds good things we're adopting: GET /auth/me, per-video progress, clearing progress, file uploads via FormData, a consistent response envelope, and 409 for duplicate emails.
  • Three PRD "MUST" features have no endpoint yet: search (FR-2.3), My List (FR-4.1), and series episodes (FR-2.2).
  • The two documents describe slightly different products — a curated Netflix-style catalog (PRD) vs user uploads YouTube-style (Viora). We need to pick one.
  • Why now: the frontend runs on a mock API that mirrors the contract, and no screens are wired to it yet — so changing the contract today is cheap for both of us.

03 · Decisions

Questions we need to settle together

  1. Who uploads content?

    PRD: only the admin curates the catalog (Netflix-style). Viora: any user uploads and deletes their own videos (YouTube-style).

    Suggestion: admin-only, as the PRD scopes it. It drops /videos/my-videos and ownership checks, which keeps the backend smaller.

  2. Do we support series with episodes?

    The PRD's personas include a "returning binger" who needs continue-watching and next-episode autoplay (FR-3.3), which needs an episode model.

    Suggestion: yes. A title is movie or series; a series has episodes[] (season, number, name, duration, videoUrl). Progress stores an optional episodeId.

  3. One set of names

    titles / titleId (PRD) or videos / videoId (Viora). Same for progress: /me/progress or /history, and positionSeconds or progress.

    Suggestion: titles, since a title can be a whole series, not one video. Either works — what matters is that we pick one and both sides use it.

  4. Can people browse without logging in?

    Viora requires a token to list videos. The PRD's success metric is "landing page → sign up → browse → play in under 60 seconds".

    Suggestion: catalog and search are public; list, progress, comments and likes require login.

  5. Field-level validation errors

    The frontend shows each error under its own field (e.g. "Email already in use" under Email). The envelope only has one message.

    Suggestion: on 400 / 409, add an errors object keyed by field name (example below).

04 · Proposal

Merged contract

Base URL http://localhost:5000/api. Protected routes send Authorization: Bearer <token>; the backend derives the user from the token — the client never sends a userId.

05 · Response shape

Envelope, with field errors

Your envelope, plus one addition so forms can show errors under the right field:

// 200 / 201 success
{ "success": true, "message": "Title added to your list", "data": { … } }

// 400 validation error, or 409 conflict
{
  "success": false,
  "message": "Please fix the highlighted fields.",
  "errors": { "email": "An account with this email already exists." }
}

Tokens

The PRD specifies a short-lived access token plus a refresh token. If we keep a single long-lived JWT for the MVP, that's fine — let's just write it down so the frontend doesn't build a refresh flow nobody implements.
